# Windows 常用命令的沙箱兼容性

2026-10-16 在 Windows x64 build 26300 上实测：权限兼容问题不只影响 Git。普通终端可用，不能推导受限 Agent 也能执行；隔离边界检测通过也不等于所有开发工具都兼容。只有 C 盘不是原因。

## 实测结果

同一套探针分别在 C 盘系统临时目录、D 盘开发目录创建中文、空格项目，在 MXC 和 AppContainer 内运行。测试不需要联网，不安装依赖，不修改用户项目。

| 操作 | MXC | AppContainer |
| --- | --- | --- |
| PowerShell 列目录、读写文本、新建目录 | 正常 | 正常 |
| PowerShell `Copy-Item`、`Move-Item`、`Remove-Item` | 拒绝访问 | 拒绝访问 |
| `System.IO` 复制、移动、删除文件和目录 | 正常 | 正常 |
| `cmd.exe /d /c echo` | 正常 | 正常 |
| 系统安装的 Node.js、`fs.realpathSync.native`、本地模块加载 | 正常 | 系统 Node.js 无法被命令查找访问；绝对路径调用也失败 |
| 项目内独立 Node.js：文件读写、真实路径、本地模块加载 | 正常 | 正常 |
| npm 版本、本地 `npm run`、隔离缓存路径 | 正常 | npm 安装位置无法被命令查找访问 |
| 用户目录内 pnpm 版本及本地 `pnpm run` | 命令查找失败 | 命令查找失败 |
| `dotnet --info` | 可运行；本机只有 runtime、无 SDK | 可运行；本机只有 runtime、无 SDK |

这张表记录当前机器和工具安装布局，不代表其他 Windows 版本、安装路径、工具版本有相同结果。没有对 Python、Java、Rust 等未准备完整运行时的工具宣称兼容。

此外，项目内 Node.js 的同步子进程探针在 AppContainer 中发生停滞：已完成 `require('node:child_process')` 并输出调用前标记，但 `execFileSync` 没有返回，其 3 秒超时也没有生效，最终由沙箱 10 秒外层超时终止。MXC 的相同探针正常。不能把“Node.js 主进程启动正常”当作子进程兼容证明。该限制仍待修复，不应建议用户通过复制 Node.js 就能解决整个工具链。

## 原因与处理

1. **PowerShell 文件系统提供程序的兼容性。** 同一项目中 `System.IO` 成功，而部分路径 cmdlet 被拒绝，与其额外处理父目录/驱动器的既有限制一致。没有凭错误文本断定唯一原生 API 调用。Agent 已优先使用专用 `copy`、`move`、`delete`、`mkdir`、`rmdir` 文件工具；需要复合脚本时可使用 `System.IO`。这些文件工具仍校验项目范围、链接及受保护目录。
2. **工具本体无法读取或执行。** 当前系统 Node.js 位于 `C:\Program Files\nodejs`，pnpm 位于宿主 `AppData\Roaming\npm`。PATH 只是搜索路径，不授予访问权。沙箱内“无法识别命令”可能是搜索时无权读取，不足以说明软件未安装。绝对路径不会绕过内核权限。MXC 和低权限 AppContainer 对宿主安装目录的实际可访问性不同；不能因为 Git 的兼容后端通过就宣称 Node.js 也可用。
3. **用户配置和缓存。** 现有隔离环境将 HOME、XDG 配置、临时目录、npm 缓存、Corepack 目录指向临时区，关闭 Git 宿主配置继承；但 USERPROFILE、APPDATA、LOCALAPPDATA 仍保留宿主位置。依赖这些变量、Windows 用户目录 API 或版本管理器的其他工具仍可能尝试访问禁止路径。不能笼统宣称所有工具的配置和缓存都已隔离兼容。
4. **子进程与网络。** 子进程继续受约束；其 IPC、运行库和路径操作需要分别验证。下载包、访问全局存储、项目外联接目标和凭据目录被拒绝，是当前限制的一部分。读取程序安装目录的兼容方案应限定到经验证的运行时，不能开放整个用户目录或全盘。普通命令失败不自动切换后端重跑，避免重复副作用；Git 的专用启动探针或实际执行中的完整 cwd 权限错误可触发恢复，运行时恢复仅自动重试严格匹配的有限只读 Git 查询组合，其他脚本不自动重跑。详情见 [Git 修复](windows-git-sandbox.md)。

应用不会调整宿主工具 ACL、自动安装或迁移运行时，也不会放开父目录或整盘权限。下述恢复流程已处理可明确判断的情况；AppContainer 的 Node.js 子进程问题仍不能宣称已修复。

## 自动恢复流程

项目自审模式下，恢复由工具执行器处理，状态通过现有任务状态及工具结果传递给模型；不依赖模型反复试错。

1. **文件操作自动替代。** 完整解析单条字面量 `New-Item -ItemType Directory`、`mkdir`、`Copy-Item`、`Move-Item`、`Remove-Item`、`rmdir`，在确认源和目标位于项目内、无链接、无保护目录且语义一致后转交专用文件工具。新目标必须不存在，复制/移动的目标父目录必须已存在，目录复制必须明确 `-Recurse`。变量、通配符、`-Force`、重定向、管道和复合脚本不改写；不把浅复制或覆盖操作改成递归复制或拒绝覆盖的其他操作。
2. **预先隔离配置缓存。** 新建命令临时区时创建空 npm 用户/全局配置及 npm、pnpm、Corepack 缓存目录，设置对应环境变量；Corepack 不自动联网下载包管理器。Git 的 HOME 和配置隔离沿用已有流程。不能保证依赖 USERPROFILE 或 Windows 用户目录 API 的其他工具都已兼容。
3. **运行时访问诊断。** 对完整解析的单条 Node、npm、pnpm、Corepack、Python、Rust、.NET、Go、Java 等有限命令，在执行原操作前仅使用 `Get-Command` 检查可发现性，不启动程序做能力探针。Git 使用已有专用启动探针和后端恢复。宿主仅检查安装路径元数据，不执行宿主程序。如果沙箱不能发现工具，先尝试已存在且通过边界检查的项目根目录、`.bin`、`node_modules/.bin` 运行时；应用不会复制宿主工具到项目。
4. **必要时批准一次并继续。** 只有确认原命令未启动、宿主可定位工具且无可用项目内候选时，自动发起现有的本机执行审批。审批展示原命令、固定安装路径后的实际命令及权限范围：本次执行具有当前用户完整本机权限，包含项目外文件与网络能力，并非仅授权某个目录。批准后同一次工具调用继续，只执行一次；拒绝或取消后不重复申请。未定位到工具不会被误判为需要扩权。
5. **部分执行不重放。** 原命令已启动后遇到权限错误或超时，保留输出和 `partial-or-unknown` 状态，不重跑、不自动转本机。同一任务内阻止再次执行相同失败命令，模型先核对已有结果，再用文件工具完成剩余操作；确需项目外访问时应单独提交剩余操作。普通非零退出、语法错误、工具缺失不触发自动扩权；诊断或隔离边界失败保持关闭。

当前恢复覆盖“程序发现失败”，不能把 `Get-Command` 成功等同于程序、DLL、配置、子进程均可访问。后者可能在实际执行阶段失败，必须遵循部分执行规则。

## 重复诊断

本地测试 `tests/windows-command-compatibility.test.ts` 输出逐项 `PROBE ... OK/FAIL`，将工具执行结果与探针本身的执行结果分开；已知限制会记录为失败项，测试套件完成不代表所有工具兼容。基础项目操作和项目内 Node.js 必须成功，子进程单独设置超时，以免挂起影响剩余项目检查。

```powershell
$env:PI_RUNNER_APPCONTAINER_TEST='1'
$env:PI_RUNNER_NATIVE_SANDBOX_TEST='1'
pnpm test tests/windows-command-compatibility.test.ts
```

测试按项目约定不纳入 Git。故障机器可用后，应对照宿主与沙箱中的工具安装位置、版本、后端、Windows build 和完整错误复测；本机结果不能代替该机器验收。各轮验证的测试计数与范围见[验收测试](acceptance-testing.md)。
